# 行情引擎复核

本轮依据仓库代码、隔离 MySQL 查询和本地浏览器 mock；不是生产压力测试，
没有启动实际交易对、修改资金或调整结算政策。

## 本轮已处理

1. **限量扫描饥饿**：原手工策略按 ID 取前 N 项，默认生成按成功检查点
   排序。持续失败且没有检查点的项可能反复占用默认名额。两类候选现改为
   按 `market_generation_attempts.last_attempt_at, pair/id` 排序，尝试互斥前
   记录数据库 UTC 时间。成功、失败、锁竞争都会轮转，成功价格检查点不动。
   独立实库测试用四个交易对、每轮两项验证轮转、无伪造检查点和手工优先。
2. **配置与发布混淆**：新币项目有真正的服务端草稿，不复用立即生效 PATCH
   冒充草稿。发布在共同命名锁和事务下复用原生成器校验、版本及审计，
   发布回执与行情配置同时提交；重复发布同修订不重新启用。
3. **状态表达**：显示读取时来源、最后价格/更新时间、读取时间、异常、
   等待接管、暂停和等待新版本。配置已启用不等于已经运行；未持续采样的
   快照不会随着浏览器计时器被误判成故障。跟随模式仍标识为平台生成行情。

## 后续优先项

### P1：准备阶段错误隔离

`src/workers/synthetic_market.rs::run_once_with_runtime` 和
`src/workers/synthetic_market/default_market.rs::run_defaults` 的逐项准备
查询、锁获取/释放仍有直接 `?`。发布阶段已有按项错误记录，但准备查询失败
可能提前结束整轮，甚至让手工批次之后的默认批次等下一轮才执行。

建议把可恢复的单交易对准备错误纳入统一结果统计，并区分全局数据库不可用。
连接级故障不宜盲目对剩余 100 项连续重试。需要故障注入、所有权丢失和锁
释放回归后实施；本轮未扩展该控制流，以免改变既有 fencing/事务行为。

### P1：容量与轮次耗时

两类生成各有 1..100 上限，目前按项串行执行，单轮使用同一个观察时刻。
公平轮转仅解决“轮不到”，不能保证大量交易对仍每秒更新。慢 Mongo/Redis、
长查询或排队可能使后续项拿到过时的观察时刻/租约，触发已有安全拒绝。

先监测每轮耗时、每对最近尝试/成功时间、锁等待、失败率和候选积压，再做
有界并发或分片。必须保留 pair 命名锁、当前分钟预留、代际和归档时序 CAS，
不能直接取消锁或无限并发。尚未做高并发/长时间故障恢复压力测试。

### P2：统一健康监控与告警

当前后台读取的是配置及运行快照，尚不是持续监控面板。本页的新鲜度诊断
不能代替金融取价资格检查，也不能证明 Redis/Mongo/WebSocket 全链路一致。
后续可聚合 worker 心跳、最近成功归档/发布、行情源延迟和补偿积压，并按
来源和故障类型告警，避免只看 WebSocket 已连接或 active_source。

### P2：预览证据与发布审核

前端已要求保存当前草稿、预览且显式确认；后端发布仍以草稿修订和实时
业务校验为权威，没有引入服务器签发的“已预览凭证”、双人审批或定时发布。
如需强制所有 API 调用者都先预览，应独立设计带有效期的预览摘要/审核契约，
不能把浏览器按钮禁用当成后端审批规则。

## 保持的边界

- 手工有效排期仍优先；手工故障不会被默认行情偷偷接管。
- 暂停只停行情生成，不撤单、不平仓、不自动停用交易。
- 初始价只在无可用历史/检查点时使用，不以发行价重置当前走势。
- 当前分钟与来源切换规则不变，不自动修补历史 K 线或重写用户订单价格。
- 生成深度、成交量和跟随路径不代表真实交易流动性；秒合约、杠杆及现货
  继续使用既有资格/版本/证据校验，本轮未放宽这些规则。

## 发布前检查

先在生产同版 MySQL 8.4 演练迁移 0142、0143，再切换 API/worker/admin。
新调度代码查询 0143 表，必须先迁移后启动；新流程依赖 0142 草稿表。

本轮没有验证 MySQL/Mongo/Redis 到真实用户订单的完整实盘链路。
