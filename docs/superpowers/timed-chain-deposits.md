# 统一充值配置与验收

充值只保留“快速充值”和“链上充值”。快速充值沿用 GMPay；链上充值采用“网络＋链上资产＋地址＋精确币种数量”占用 30 分钟。不同金额可共用地址，同金额使用其他地址；该金额的地址全部占用时提示重试，不添加尾数、不换算法币。已付款组合也保留到原截止时间。

## 启用步骤

1. 应用尚未执行的迁移 `0158_timed_chain_deposits.sql`、`0159_timed_deposit_text_identity.sql` 和 `0160_independent_recharge_addresses.sql`。不要修改已应用文件。0160 将收款地址从旧永久库存中独立出来，自行生成编号，保留已有链上订单的地址引用。
2. 配置现有 `CREDENTIAL_ENCRYPTION_KEY`，要求 32 字节并持久保管。节点地址与 API 密钥加密存库；后台留空表示保留，不回显原值。
3. 打开“钱包资产 → 链上充值 → 网络与收款配置”，选择 Ethereum、Base、Tron、Bitcoin 或 Solana，按“节点接入 → 监听币种 → 收款地址 → 扫描与接单”指引操作。点击“配置节点”或“编辑监听配置”，使用预填的免费默认渠道，或配置自有节点与确认数。
4. 在“监听币种”点击“新增监听币种”。例如 Ethereum 先添加原生 ETH（自动填 18 位精度），再分别选择 USDT、USDC，填写各自在 Ethereum 的真实主网合约和 decimals，后续仍可继续添加。币种选项来自平台资产；若未找到，先在资产管理创建后刷新本页。可显式选择下文主网预设填入合约和精度，也可手动填写；资产简称不代表链上身份。已有映射通过“编辑 / 启停”管理，合约与精度固定并显示不可修改原因。
5. 在“收款地址”点击“添加收款地址”，在独立面板粘贴地址，每行一个，单次最多 500 个。每网可先放 10 个，后续继续添加，没有 10 个硬上限。重复地址跳过，已停用地址不会因重复导入重新启用；任一地址无效则整批不保存。无需库存编号或二次纳入。Ethereum/Base 即使使用相同地址，也要分别添加到各自网络。
6. 检查平台资产的充值开关、最低充值数量、固定手续费和精度。数量必须高于手续费且满足链上及钱包精度，钱包最多 18 位小数。旧网络白名单、旧地址库存和地址组不再参与充值准入；“提现网络”只维护提现所需目录。
7. 开启“接受新充值订单”，等待最近追上区块的成功时间。节点未同步、报错或成功时间超过 120 秒时，不接受新订单。节点已配置时会持续监听，关闭接单开关、停用地址或资产都不影响已创建订单的到账核对。配置更新及新增地址会清除就绪状态，重新追上区块后才能接单。

编辑面板都有“取消编辑”；填写后关闭会提示是否放弃草稿。保存冲突保留草稿和原因，取消后刷新再重新编辑即可读取最新版本。网络选择不会再因为改动一个表单就被无提示锁死。

后台“订单与到账核对”查看订单和处理归属歧义，“入账流水”查看已入账记录；“快速充值”工作区集中维护 GMPay 配置和订单。用户端先选择链上币种与网络，再输入例如 100 USDT 或 50 ETH 的数量创建订单。

测试环境已取消旧永久地址兼容：旧分配 API、旧库存 CRUD 和旧观测到账 API 均退役。旧网关充值回执进入死信，不按旧地址归属自动加币；已有历史账务保留。提现业务仍使用原网关流程。

五网络配置边界：

| 网络 | 本批资产 | 所需节点能力 |
|---|---|---|
| Ethereum | ETH、明确配置的 ERC20 | 主网 chainId 1；完整区块、按 blockHash 的日志、decimals；原生 ETH 还要求 `debug_traceBlockByHash` 的 `callTracer` |
| Base | 直接转入的 ETH、明确配置的 ERC20 | 主网 chainId 8453；区块交易哈希、批量 `eth_getTransactionByHash`、`eth_getTransactionReceipt` 成功回执；ERC20 使用按 blockHash 的日志与 decimals。内置免费渠道直接读取完整交易区块；自定义渠道使用交易批次。不需要 debug/trace，合约内部 ETH 转账不会自动到账 |
| Tron | 明确配置的 TRC20 | 主网 FullNode，`getnowblock`、`getblockbynum`、`gettransactioninfobyblocknum`、合约精度常量调用；原生 TRX 暂不开放 |
| Bitcoin | BTC | 已同步的主网 Bitcoin Core JSON-RPC，`getblockchaininfo`、`getblockhash`、`getblock` verbosity 2；使用可访问的历史区块，逐 vout 匹配，coinbase 不作为充值 |
| Solana | SOL、经典 SPL Token | mainnet-beta 的完整 finalized `jsonParsed` 区块、inner instructions、mint 元数据、slot/区块时间；Token2022 暂不开放 |

自定义渠道的 Base 原生 ETH 使用普通 RPC：以 `eth_getBlockByNumber(height, false)` 读取交易哈希，每组最多 25 笔批量查询交易，仅为正金额且直接转入受监听地址的交易查询回执，核对成功状态、区块哈希/高度、交易哈希/位置及双方地址后生成到账证据。批量响应按 ID 还原顺序，漏项、重复或错误结果使整块失败。失败交易、零金额、自转账、合约创建和合约内部转账不生成原生充值证据。ERC20 处理方式不变；Ethereum 仍支持调用树和内部 ETH 转账。

自定义渠道含原生资产的 Base 每轮最多处理 4 个区块，所有请求仍经过渠道/Key 持久节流。批量查询不能视为增加了账户吞吐；套餐限流时继续冷却重试。执行 0167 后，交易批次收到 HTTP 429 会在保留冷却的同时缩小该 Key 的批量上限，例如 25→12→6→3→1；成功和重启保留上限，后续每轮区块数也随之缩小。替换 Key 或渠道地址后重新学习，普通留空保存不重置。需在部署后观察是否持续追上区块，不能仅凭单次接口成功宣布充值恢复。

仅替换 Base 原生 RPC 的初版改动不需要迁移；若发布下方分流功能，必须执行 0165，旧 trace 故障升级修复还需执行 0166。这些改动不会自动跳过历史区块；0166 仅清除明确匹配的旧 Base trace 渠道错误，其他冷却全部保留。已有直接转账沿用原调用树根事件的去重编号，补扫不会重新创建同一笔证据；已经保存的内部转账证据不删除，但尚未观测到的内部 ETH 付款不在新的 Base 自动扫描范围。运营需明确告知用户仅使用直接转账充值 Base ETH。发布后检查完整扫描成功并追上区块；有历史积压时保留补扫，不要用跳块替代恢复。

### 更新后渠道状态仍显示 debug_traceBlockByHash

“渠道状态”读取数据库里保存的最近错误，看到该文字不等于新版又调用了 trace。旧版因 trace 权限失败写入的共享渠道冷却可能持续约 64 分钟；升级到 0165 会保留它，导致两路在发送普通 RPC 前就被排除。即使冷却已经到期，只有该渠道完整扫描成功后才会清除旧文字，未被选中的备用渠道可能一直显示历史错误。

执行新增的 `0166_retire_base_trace_cooldown.sql`：仅对 Base 中错误恰为 `RPC 方法 debug_traceBlockByHash 失败，请检查渠道权限和额度` 的渠道清除旧故障、冷却、连续计数及旧成功时间。不会修改 RPC 地址或 Key，不会开启停用渠道，不会动区块游标、历史补扫、恢复请求或余额；其他错误以及 Key 的 429/401 冷却保留。迁移完成不代表已恢复收款，仍要确认对应分流重新扫描成功并持续追上区块。

升级顺序：停止旧扫描 worker → 拉取含 0166 的版本并重新构建后端/迁移器（或拉取已构建的新镜像）→ 使用同版迁移器执行所有待应用迁移 → 启动新版 worker。根目录 `build.rs` 已补充迁移目录变化监听，容器也会复制它，避免新增 SQL 文件时增量构建仍嵌入旧迁移列表。不要只重启旧镜像。如果确认新运行日志在新版本仍调用 trace，继续核实实际进程/镜像版本和日志网络，不要靠反复清冷却掩盖问题。

节点凭据可放在节点 URL 的受控鉴权路径中；API 密钥字段在 Tron 使用 `TRON-PRO-API-KEY`，其他网络使用 Bearer。Bitcoin Core 的用户密码鉴权可使用节点 URL 的 Basic Auth 信息，务必使用受信网络或 TLS 代理。所有地址只需要收款地址，系统不接收私钥。

### Base 普通交易查询 HTTP 429（2026-10-29）

月额度充足仍可能触发短时间请求频率限制。Nodies Free Plan 的公开页面只标注较低速率，未公布具体 RPS；不能把月剩余额度换算成已获准的瞬时吞吐。新版本在每次等待后重新检查最新渠道/Key 发送时间，避免其他响应延长等待时间或进程调度暂停后，旧预留请求集中发送；同时根据交易批次的 429 反馈保存较小批次。仍遵守服务商 Retry-After 和共享冷却，不通过重新提交或清错误绕过限制。

发布前停止旧充值扫描 worker，构建含 `0167_deposit_rpc_batch_limit.sql` 的新后端/迁移器，执行所有待应用迁移后启动新版。0167 只为 Key 增加初始值为 25 的内部批量上限，保留现有错误、冷却、游标和资金数据；迁移后需要等待真实冷却结束，再观察完整扫描是否持续成功。更小批量并不保证 Free Plan 能持续跟上全链逐笔查询，极低速率下密集区块仍可能超时，需要核对服务商实际吞吐或使用有完整交易区块权限的节点。

Nodies 使用 URL 参数 `apikey` 或 `x-api-key` 请求头鉴权。当前配置推荐使用 `https://lb.nodies.app/v2/base?apikey={API_KEY}` 模板，实际密钥分别填入 Key 槽；若 URL 已写死某个 Key，切换槽位不会替换 URL 中的值。后台“API Key 已配置”只代表本地保存了密钥，不能证明服务商识别了正确账户。多个 Key 也不代表独立账户额度。

## Base ETH 与 ERC20 独立监听（2026-10-28）

Base 分为 **ETH 原生币** 和 **ERC20 代币（包括 USDC）** 两路，各自保存实时区块、历史补扫、错误、租约和接单状态，并由独立定时循环执行。ETH 专用方法失败或耗时较长时，ERC20 仍可推进、入账并接收新订单；反向同样隔离。所有 ERC20 目前共用代币一路，并非每个合约单独一条。

后台分别展示两路高度和错误，允许单独点击“恢复 ETH 到最新区块”或“恢复 ERC20 到最新区块”。恢复弹窗固定所选类别和版本，只对该路执行补扫/跳过。旧接口省略 `stream` 时仍按整网操作，两路都会排队；跳过仍需明确确认历史到账可能遗漏。配置节点、币种或新增地址时，两路都需要重新扫描确认。

两路共用已有 RPC/Key 池和请求节流。方法能力错误与整轮超时只冷却对应分流；真实 HTTP 429、鉴权或节点连接故障仍使用共享冷却，不能借分流突破服务商额度。共享额度耗尽或全部节点不可用时，两路仍可能一起延迟。ETH 仅支持直接转账的限制没有改变。

发布顺序：**先停止旧版充值扫描 worker，执行 `0165_base_deposit_scan_streams.sql`，再同版发布后端和后台并启动 worker。** 迁移把原实时/历史游标及排队恢复复制到两路，清除准入新鲜度和旧租约；不会从最新高度重新开始，也不删除订单或证据。两路分别追上后，按币种恢复接单。不要混跑新旧 worker。回滚前须暂停扫描、核对两路进度并审查统一恢复点，不能直接把迁移前遗留的 Base 游标当成当前进度。

新增 `0168_deposit_rpc_presets.sql` 后，同版更新后端、充值扫描 worker 和后台。发布时停止旧 worker，使用新版迁移器执行全部待应用迁移后再启动。迁移只增加预设身份字段，原自定义渠道、加密密钥、真实冷却和实时/历史进度均保留。完整的 1Panel compose 更新会先运行 `migrate` 服务；只重启 API 不会执行迁移。

|---|---|---|
| Base | PublicNode 主用、dRPC 备用 | ETH 直接转账、USDC 等已配置 ERC20；整块读取减少逐笔交易请求 |
| Ethereum | 免费账号模板：Chainnodes；SolidRPC 可选备用 | 需自行申请 API Key；官方文档提供区块 callTracer，尚未用实际账号验证。dRPC 匿名渠道不再默认推荐 |

Base、Bitcoin、Tron、Solana 的默认项免注册、免 API Key。首次打开监听配置会生成草稿；已有配置点击“补充免费默认渠道”追加未存在的默认项，不覆盖自有节点。Ethereum 新配置改为账号模板草稿，流程见下节。填写操作原因并确认保存后生效，不自动打开接单。仍需配置监听币种、真实收款地址与平台充值开关，再等完整扫描成功。未配置的网络不会仅因目录存在就自动请求节点。

Base 官方及 Solana 官方公共节点仍可选择，但本次探测完整扫描所需请求遇到429，只列为低频测试选项，不预填为默认。每个渠道在界面展示公开地址、官方说明链接及适用限制。样本测试不代表长期吞吐、历史可用范围或 SLA；Ethereum 免费 trace 被拒绝时会停止该轮扫描，不能悄悄改成仅识别直接转账。

选择免费预设会清除该渠道旧密钥及被省略的额外凭据，只保留一个匿名槽，避免把自有 Key 发送给公共服务。相同预设重复保存保留冷却和已学习状态；切回“自定义 RPC / 自有 API Key”可自行管理地址与凭据。免费预设的请求间隔同步控制匿名槽。无需填 Key 仍需服务端 `CREDENTIAL_ENCRYPTION_KEY` 加密保存节点地址。

Base 默认预设读取 `eth_getBlockByNumber(height,true)`，再仅核对实际匹配收款地址的成功回执；不再逐笔请求全区块所有交易。自定义/Nodies 的旧方式继续保留，避免调用其套餐不支持的完整交易块方法。两条路径保持同一到账证据编号及严格校验，换源不会重复入账或跳过历史。ETH 与 ERC20 继续独立扫描并共用节流；真实429继续冷却。

Base 币种模板补充 ETH 和原生 USDC（`0x833589fcd6edb6e08f4c7c32d4f71b54bda02913`，6 位精度），均只填草稿。USDC 合约以 Circle 官方地址表为依据，不能换成桥接币或其他网络合约。Solana 请求允许 V1，未知显式交易版本仍停止扫描，不能用忽略交易来维持“健康”状态。

官方来源与低频探测结果保存于本任务 research/providers.md；公共地址来自 PublicNode、dRPC、TronGrid 及链官方文档。持续追块和实链到账需部署后逐网观察，本轮没有生产数据库修改或真实付款。

## Ethereum 免费账号主备渠道（2026-10-29）

dRPC 匿名节点曾在单次探测中返回完整 trace，但实际监听出现 429；这不能作为免费权限或持续吞吐保证。保留其已有预设身份及配置，取消新配置默认推荐，不清除旧错误、冷却或进度。没有新增迁移，仍需同版更新后端目录与后台；此前未应用的迁移照常执行。

| 账号模板 | 官方免费层说明 | 用法 |
|---|---|---|
| Chainnodes | Core 每月 1250 万请求、25 RPS，包含 debug/trace | 首次 Ethereum 配置的草稿；申请自己的 Key 后保存 |
| SolidRPC | 每日 1 万次响应，debug/trace 按单次计数 | 可选短时备用，额度不足以单独保证持续全链扫描 |

后台「充值配置 → Ethereum → 编辑监听配置」新增「免费账号渠道」：从官方申请入口获取 Key，选择模板后点「添加所选账号渠道」。节点地址和间隔自动填入，Key 填在该渠道的独立 API Key 框，不要替换 URL 中的 `{API_KEY}`。服务端会编码后填入 URL，并使用既有加密存储、主备切换和持久冷却；不是请求头 Bearer 鉴权。

Chainnodes 模板为 `https://mainnet.chainnodes.org/{API_KEY}`；SolidRPC 为 `https://rpc.solidrpc.io/{API_KEY}/evm/1`，须使用 RPC API Key，不能填其管理用 Personal Access Token。官方资料分别为 [Chainnodes 价格与免费层](https://www.chainnodes.org/pricing)、[区块 trace](https://www.chainnodes.org/docs/ethereum/debug_traceBlockByHash)、[SolidRPC 接入](https://solidrpc.io/docs)、[trace](https://solidrpc.io/docs/tracing)。按当前控制台确认额度；多个同账户 Key 不会增加账户总额度。

追加账号模板不会改动已有渠道、密钥或接单开关。同一草稿内已添加的模板不能重复追加；保存后它属于普通自定义渠道，系统不会根据隐藏地址猜测其服务商。切换某条渠道的服务商模板会新建空白凭据，确认保存时替换原凭据，不把旧 Key 转发到新服务商；未切换的渠道留空仍保留原值。409 保留草稿与原因，取消不写入。

这两个模板已核对官方文档，**尚未使用实际账号 Key 验证完整响应、历史权限或持续追块**。保存后只有完整扫描成功才恢复健康状态。Ethereum 继续严格核对交易哈希、完整调用树和区块连续性；不支持的返回格式停止该轮，不降低为只识别直接转账。新增渠道也不会自动跳过积压历史。

本轮匿名候选 Tenderly、OnFinality、Alchemy、Blast、MeowRPC、LlamaRPC、Merkle、0xRPC 均未通过完整能力探测，未作为可用默认项加入。Tenderly 当前 Node RPC 文档说明无免费层；Alchemy Debug API 要求付费计划，因此未列入新免费账号推荐。完整官方来源和脱敏样本见 `10-29-ethereum-rpc-failover/research/providers.md`。

## 扫描状态与支付方式就绪

配置页将每个“网络 / 币种”作为一个支付方式，例如 Ethereum / ETH、Ethereum / USDT。指引显示当前可收款数量；币种下方列出平台充值未开启、网络暂停接单、缺少启用地址、扫描异常等全部待处理项。

| 扫描状态 | 含义与处理 |
|---|---|
| 未配置节点 | 先保存当前网络的节点地址与凭据 |
| 等待扫描确认 | 配置已保存，等待后台扫描器核验并追上区块 |
| 扫描异常 | 检查页面错误、节点权限/额度及资产身份，修复后扫描器自动重试 |
| 扫描状态已过期 | 超过 120 秒没有成功追上区块，检查后台任务和节点 |
| 已追上区块 | 服务端检查时处于有效窗口；仍需满足币种、地址和接单开关条件 |
| 状态待刷新 | 当前读取失败或正在刷新，旧快照不能作为可用性依据 |

页面展示持久扫描区块高度（Solana 显示 slot）、最近追上时间和服务端检查时间。新鲜度由数据库时钟判断；页面每 15 秒在可见且无编辑、确认或写操作时刷新，也可手动刷新。填写表单或地址启停原因时暂停刷新，避免替换正在确认的内容。新订单仍由服务端实时校验，页面显示不是特定金额地址容量的承诺。

这些状态来自实际扫描器记录，点击刷新不会进行节点连接测试或跳过历史区块。节点保存成功不代表已经具备收款能力，仍应等待 worker 的成功结果。

本轮借鉴 GMPay Edge 的节点、资产、地址分层和就绪原因展示；保留本项目完整区块扫描、持久游标、精确数量及 30 分钟规则。没有新增 WebSocket、Webhook、交易所支付或法币报价。接口新增扫描快照字段，后台前端和后端应同版发布；本轮无需新增数据库迁移。

## 自动入账与人工核对

- 一笔已执行且确认达标的转账，只有在网络、合约/mint、收款地址、精确数量、链上付款时间都匹配唯一订单且无歧义时自动入账。
- 链上及时付款但扫描较晚，仍按历史付款窗口匹配。客户端倒计时和扫描时间都不决定资金归属。
- 30 分钟到期立即释放组合。此前有未解决的过期未付订单时，后续同组合到账进入核对；它可能是旧用户迟付，也可能是新用户正常付款。
- 错额、分笔、迟付和重复多付款分别保留证据，不自动合并。区块时间只有秒级时，下单同秒且先后无法证明的付款也需人工核对。
- 后台可按用户提供的完整充值订单号查找，读取对应内部编号。核对页面要求运营明确填写目标内部订单编号并读取验证；不会把候选订单自动当成付款归属。
- 人工入账仍不能绕过网络/资产/地址、确认数、钱包精度和单次入账约束。允许有依据地处理迟付、错额或下单同秒的款项；使用实际到账量扣除订单手续费，原预填金额保留。
- “排除证据”只是不入账，不退款、不转出资金，也不删除过期未付历史。没有充分证据消除迟付可能时，同组合后续付款仍需核对。
- 如需冲正，使用现有已入账充值流水的冲正流程；订单读取会反映冲正状态。

权限分离：`wallet.networks` 管节点/资产配置，`wallet.address_pool` 管共享地址，`wallet.deposits.read` 查订单/到账证据，`wallet.deposits.review` 执行人工核对。

## 中断与恢复

正常重启保留持久游标；重复扫描不会重复加币。暂时性节点错误不推进游标，修复节点后会重试。停用地址/资产只影响新订单；历史监听身份保留。

已存在订单但游标缺失，或确认区块发生重组时，监听停止并关闭新订单准入。不要清空订单、删除证据或通过数据库直接修改游标。本版本没有自动深度重组恢复入口：先关闭新订单接单并由维护人员暂停相应监听 worker、保存数据库与链证据、对账受影响已入账记录并通过原冲正流程处理，再由维护人员审查恢复高度与哈希并恢复游标。接单开关不停止扫描，不能将其当成维护暂停开关。恢复范围必须覆盖未处理历史；需要修正已存在证据时应单独实施受审计的数据修复。

### 手动恢复到最新区块

应用 `0163_deposit_scanner_recovery.sql` 并同版发布后端与管理后台后，在“链上充值 → 网络与收款配置 → 网络与监听”点击“恢复到最新区块”。需要网络配置写权限；未建立游标、未配置节点或已有排队请求时不可重复提交。

- **双进度（默认）**：先跳到最新已确认区块，实时扫描成功后可恢复接单；旧区间保留并限速补扫，页面分别显示实时高度与历史进度/目标。重复恢复会扩展原补扫范围，不丢弃最早未完成区间。
- **手动跳过**：勾选风险确认并填写原因后，放弃原进度到目标之间的扫描，也会清除已有补扫任务。该区间的充值可能无法自动识别，需另行核对；订单、到账证据和已入账记录不会删除。

两种方式都只跳到符合确认深度的高度（Solana 使用 finalized slot）。提交先排队，节点身份、旧锚点和目标验证成功后才应用；节点失败保留原进度并重试。请求与实际应用都记录管理员、原因和前后进度。普通重启仍从原进度继续，不会自动丢弃历史。

实时与历史共用现有主备渠道及 Key 限速；历史每轮之间至少间隔15秒，实时扫描优先。历史节点临时故障单独显示并重试；若历史区块哈希、连续性或账务异常，会阻止新订单准入，不能用实时健康状态覆盖。补扫发现的过期/取消订单付款仍按原到账归属规则处理，重复交易不会重复加币。

缺失游标或确认区块重组不能靠此按钮绕过，仍按上方对账恢复流程处理。

### TronGrid HTTP 监听异常排查

新版错误会保留网络、调用接口与 HTTP 状态，例如 `tron /wallet/getnowblock HTTP 403`。节点 API 密钥已配置只代表数据库中存在凭据，不代表服务商已接受该密钥或允许当前请求。

- `401`：检查 API Key 的有效性和凭据配置。
- `403`：核查服务商控制台的拒绝原因，包括 Key 的服务器出口 IP / 接口限制、请求频率和调用额度；不能仅凭 403 判定密钥失效。
- `404 / 405`：检查基础地址及接口支持；TronGrid 主网基础地址应为 `https://api.trongrid.io`，不要自行追加 `/wallet` 或 `/jsonrpc`，监听器会追加具体 REST 接口。
- `429`：检查用量、配额及同一 Key 是否被其他服务共用；应处理限制后等待自动重试，反复重启不会增加额度。
- `5xx`：检查节点服务或上游网关状态。

核查接口权限时包含 `getblockbynum`、`getnowblock`、`triggerconstantcontract` 和 `gettransactioninfobyblocknum`。更新后端后等待下一轮扫描，再从后台复制完整的脱敏错误用于定位；不要发送 API Key。HTTP 失败保留原游标，不应通过清空游标或降低确认数处理。该诊断改动无需数据库迁移或前端更新。

## 主备渠道与多个 API Key

应用 `0162_deposit_scanner_providers.sql` 后，现有节点和加密密钥成为“默认渠道/默认凭据”，原扫描高度不变。后台与后端需同版更新。新版未配置网络会预填免费默认渠道，也可在“编辑监听配置”添加自定义渠道及多个 Key。

- 每网最多10个渠道，每渠道最多10个凭据槽。优先级越小越先尝试，相同优先级按创建顺序。
- 渠道与 Key 的请求间隔都限制在100至2000毫秒，默认250毫秒；两级共同限制请求频率，补扫批次随间隔收缩。间隔越大请求越慢，过低额度的节点仍可能无法追上链。
- TronGrid 使用基础地址及 Key 请求头；Alchemy/Helius 等 URL 鉴权渠道可保留预设的 `{API_KEY}` 模板，为该渠道添加多个 Key，系统会编码替换，不重复发送 Bearer。
- 已保存节点和 Key 不回显，留空保留，清除密钥需显式开关。无鉴权公共节点保留一个空凭据槽；URL 模板不允许空 Key。
- 429依据 Retry-After 和指数退避冷却 Key，401也冷却该 Key；连接失败、403及5xx等冷却渠道。冷却保存到数据库，重启不会清空；未替换密钥的普通保存也不会清空。
- 每轮先按渠道优先级各尝试一个可用 Key，再轮转各渠道的次级 Key，避免同一服务商的失效 Key 占满重试机会。一轮最多尝试10组渠道/Key，仍受45秒总时限及单次35秒时限约束；慢请求可能使后续渠道等到下一轮。备用接管前重新核对主网、资产精度和原游标哈希。链身份/区块连续性/账务异常仍停止网络并等待核对，不通过换源掩盖。
- 全部不可用时保留进度并停止新订单准入；可用渠道恢复后继续补扫。不要清空游标。多个 Key 不意味着服务商账户额度叠加，也不能保证外部节点永不故障。

配置页优先显示 RPC 渠道、可尝试数量和凭据槽数，并将扫描进度单独展示。首选/备用标签表示配置顺序，不是实时使用记录；“可尝试”不等于追块成功。Base 同时展示 ETH 和 ERC20/USDC 各自的冷却原因。密钥错误可展开查看，过期错误在成功前保留为历史提示。

编辑时可预览主备顺序、展开/收起单个或全部渠道；新增渠道会自动展开，折叠不丢失已填 Key。保存仍需原因，冲突保留草稿。新版 API 增加分流状态字段，旧版 API 缺少该字段时显示“分流状态待更新”，请同版更新 API、worker 和后台。本次优化没有新增迁移。Bitcoin、Solana 的游标校验使用精简区块响应，真实充值扫描仍要求完整交易证据。
